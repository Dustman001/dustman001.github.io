Data architecture · API

Universal Data Model: one schema for three platforms

30+ management companies · ~500 communities across the US

Problem

Property management, a community platform and suite management each kept their own copy of communities, people and units. The same resident could exist three times with different data.

What I built

The central canonical model in SQL Server, fed by change-data-capture events, plus typed Azure Functions endpoints for communities, people, units, work orders, violations and notifications.

Key decisions

Unified people across systems by normalized email scoped to each management company. Put every endpoint behind one shared API-key validation service. Built a React 18 consumer app.

Event streaming

Change Data Capture event system

Problem

Downstream services needed to react when data changed in each client's database, without touching the legacy applications that wrote to it.

What I built

A timer-triggered Azure Functions listener (dotnet-isolated) that reads SQL Server CDC tables in every client database and publishes "entity changed" events to Azure Event Hub.

Key decisions

Tracked the log sequence number (LSN) per database so no change is processed twice. Made batch size configurable. Added health and liveness probes so Kubernetes can restart a stuck listener.

Messaging · Resilience

Multi-channel notification service

Problem

Every change in the database could matter to different residents and staff. The right people had to hear about it by email, SMS or push, even when a provider was down.

What I built

A service that resolves recipients by community, role and subscription rules, queues each message on Azure Service Bus, and delivers through SendGrid, Twilio and push, with tracking in Cosmos DB.

Key decisions

Polly v8 policies for provider failures, Service Bus for retries, and a sandbox mode to test without spending credits. Found and fixed a production bug that silently dropped messages for non-admin users by adding logging at every pipeline stage.

End-to-end feature

In-App Instant Access

Problem

Residents and visitors needed to request building access from the app, and managers needed to approve it without staff manually granting each one.

What I built

The complete feature: SQL schema, REST endpoints for the approval flow, an Azure Service Bus queue, a background scheduler that grants access automatically, and the React/TypeScript interface.

Key decisions

Decoupled approval from granting with a queue, so a slow access-control system never blocks the user. The scheduler handles timed access windows on its own.
